# 架构设计

## 说明

当前仓库尚未包含源码，因此本文档描述的是推荐架构基线。后续确定真实技术栈后，应将本文件更新为“事实架构”，包括实际目录、服务、数据库、接口和部署拓扑。

## 架构目标

- 支持老年用户、家庭成员、社区工作者和管理员的差异化使用场景。
- 将训练内容、训练过程、协同关系、权限控制和统计分析清晰分层。
- 保护个人信息，避免授权边界不清。
- 支持从最小可用版本逐步扩展到多端、多社区、多内容类型。
- 保持开发、测试、部署和运维可理解、可验证。

## 推荐系统分层

```text
客户端层
  老年用户端 / 家庭端 / 社区工作端 / 管理后台

接口层
  API 网关或后端路由 / 鉴权中间件 / 参数校验 / 响应封装

业务层
  用户与权限 / 情景训练 / 内容管理 / 家庭协同 / 社区活动 / 统计分析

数据层
  用户数据 / 训练内容 / 训练记录 / 授权关系 / 活动数据 / 审计日志

基础设施层
  数据库 / 对象存储 / 缓存 / 日志 / 监控 / 部署配置
```

## 推荐模块划分

### 用户与权限模块

职责：

- 管理账号、角色、登录态和权限。
- 管理家庭授权关系和社区服务关系。
- 为其他模块提供统一的身份和授权判断。

边界：

- 不直接处理训练题目逻辑。
- 不向调用方泄露超过授权范围的用户数据。

### 情景训练模块

职责：

- 提供训练场景、题目、选项、判断和反馈。
- 记录训练开始、提交、完成和复盘状态。
- 计算训练结果和薄弱知识点。

边界：

- 不直接决定家庭成员能看到什么，应通过授权模块判断。
- 不负责内容审核流程，只消费已发布内容。

### 内容管理模块

职责：

- 管理诈骗主题、情景脚本、题目、答案、解释和风险提示。
- 支持草稿、审核、发布、下线和版本记录。
- 为训练模块提供已发布内容。

边界：

- 不记录用户训练结果。
- 不绕过审核直接发布面向用户的内容。

### 家庭协同模块

职责：

- 管理家庭绑定、授权范围、提醒和陪伴建议。
- 向家庭成员展示授权范围内的训练摘要。
- 支持家庭沟通建议和风险提醒。

边界：

- 不展示未经授权的训练细节。
- 不替代正式报警、金融冻结或法律处理。

### 社区共育模块

职责：

- 管理社区活动、课程、用户分组和训练任务。
- 提供群体汇总统计和活动复盘。
- 支持宣教材料沉淀。

边界：

- 默认使用汇总数据，避免暴露个人细节。
- 如需查看个人数据，必须有明确授权和审计。

### 统计与审计模块

职责：

- 汇总训练完成率、主题掌握情况、常见错误类型。
- 记录登录、授权、内容发布、数据导出等关键操作。
- 支持问题排查和安全审计。

边界：

- 日志不能保存明文密码、令牌、身份证号等敏感信息。
- 统计报表应优先使用匿名化或汇总化数据。

## 推荐数据对象

以下为概念模型，具体字段以后续数据库设计为准。

- User：用户账号、基础资料、状态。
- Role：角色定义。
- Permission：权限点。
- FamilyLink：家庭绑定关系、授权范围、有效期。
- Community：社区组织。
- CommunityMembership：用户与社区关系。
- Scenario：训练场景。
- Question：题目和选项。
- KnowledgePoint：反诈知识点。
- TrainingSession：一次训练过程。
- TrainingResult：训练结果、得分、错误类型、复盘建议。
- Activity：社区课程或活动。
- AuditLog：关键操作日志。

## 典型数据流

### 老年用户完成训练

1. 用户登录并选择训练主题。
2. 系统根据主题、难度和发布状态加载场景内容。
3. 用户完成互动选择。
4. 后端校验提交内容并生成结果。
5. 系统保存训练记录和复盘建议。
6. 用户查看反馈。
7. 若用户授权，家庭端或社区端可查看摘要数据。

### 家庭成员查看进度

1. 家庭成员登录。
2. 系统校验家庭绑定关系和授权范围。
3. 后端查询训练摘要，而非默认返回全部答题细节。
4. 前端展示进度、薄弱主题和陪伴建议。
5. 访问行为写入审计日志。

### 社区活动统计

1. 社区工作者创建活动并分配训练内容。
2. 用户完成训练任务。
3. 系统生成活动维度汇总统计。
4. 社区工作者查看完成率、常见错误和建议讲解重点。
5. 如导出数据，应触发权限校验和审计记录。

## API 设计原则

- 接口命名应围绕资源和动作，保持一致。
- 所有写操作必须校验身份、权限和参数。
- 响应应包含可理解的错误信息，避免只返回内部异常。
- 分页、排序、过滤应有统一约定。
- 不在 URL、日志或错误信息中暴露敏感数据。
- API 契约确定后，应在 `docs/api/` 中补充详细说明。

## 技术选型原则

当前不强行绑定具体技术栈。选型时建议遵循：

- 团队熟悉优先，降低开发和维护成本。
- 安全和可维护性优先于短期炫技。
- 前后端边界明确，接口契约稳定。
- 数据库优先选择可靠、易备份、易迁移的方案。
- 涉及 AI、语音或第三方服务时，必须明确失败降级方案和隐私边界。

## 部署建议

最小可用阶段可采用单体后端加独立前端部署，数据库独立管理。后续用户量、组织层级或内容规模增长后，再考虑拆分服务。

推荐环境：

- development：本地开发。
- test：测试验证。
- staging：上线前预发布。
- production：正式环境。

每个环境应独立配置数据库、密钥、日志和第三方服务，不得共用生产敏感配置。

## 架构风险

- 家庭协同容易越界为监控功能，应始终围绕授权和陪伴。
- 社区统计容易暴露个人信息，应优先汇总化。
- 情景内容如果缺少审核，可能传播错误或过度恐吓信息。
- 后期引入 AI 对话时，可能产生不稳定建议，应设置边界、审核和免责声明。
- 老年用户端如果交互复杂，会降低使用率。
